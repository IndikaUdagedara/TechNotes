# New Relic NRQL Alert Streaming Methods: Event Flow vs Timer

New Relic NRQL alert conditions don't evaluate data instantly — they collect
data into "aggregation windows" first, then collapse each window into a
single value and check it against the threshold. The "streaming method"
controls how New Relic decides a window is complete and ready to evaluate.
Two main methods: Event Flow (default) and Event Timer. A legacy third
method, Cadence, uses wall-clock ticks and is discouraged.

## Event Flow (default)

Rule: a window `[start, end)` is only aggregated once a data point arrives
with a timestamp `>= end + delay`. Progress is driven by *later timestamps
arriving*, not by time itself passing. If no new data shows up, the window
just stays open and waits.

Best for: frequent, steady, in-order data — APM agent metrics, infra agent
metrics, live CloudWatch streaming metrics.

Caution: if data points can be >65 minutes apart, use Event Timer instead.

**Worked example**

Window duration = 1 minute, delay = 2 minutes. Windows are fixed,
epoch/wall-clock-aligned buckets: `[12:00:00-12:01:00)`, `[12:01:00-12:02:00)`,
etc. — NOT anchored to whenever the first data point in that window happens
to arrive. This fixed alignment is what makes TIMESERIES charts, loss-of-signal
detection, and gap filling consistent across signals and restarts.

Data points arriving every 30s:

| Point | Timestamp |
|---|---|
| data1 | 12:00:33 |
| data2 | 12:01:03 |
| data3 | 12:01:33 |
| data4 | 12:02:03 |
| data5 | 12:02:33 |
| data6 | 12:03:03 |
| data7 | 12:03:33 |
| data8 | 12:04:03 |
| data9 | 12:04:33 |
| data10 | 12:05:03 |

Bucketed into windows:

| Window | Contains | Closes when timestamp >= | Triggered by |
|---|---|---|---|
| [12:00-12:01) | data1 | 12:03:00 | data6 (12:03:03) |
| [12:01-12:02) | data2, data3 | 12:04:00 | data8 (12:04:03) |
| [12:02-12:03) | data4, data5 | 12:05:00 | data10 (12:05:03) |
| [12:03-12:04) | data6, data7 | 12:06:00 | not yet (still open) |
| [12:04-12:05) | data8, data9 | 12:07:00 | not yet (still open) |
| [12:05-12:06) | data10 | 12:08:00 | not yet (still open) |

Key insight: the point that triggers a window's closure is never itself a
member of that window — it belongs to a later window, which will in turn be
closed by some future point. With steady 30s data and a 2-minute delay, each
window waits for roughly 4 more data points to arrive after its own window
ends before it's finally evaluated.

## Event Timer

Rule: when a data point lands in a window, a countdown timer starts (set by
the "timer" value). Every new data point for that same window resets the
timer. If the timer ever reaches zero with no new arrivals, the window is
aggregated as-is.

Best for: sporadic, bursty, or infrequent data — error counts, polled cloud
integration data (GCP/Azure/AWS polling), usage stats. Progress is driven by
a pause/silence in arrivals, rather than by a later timestamp showing up.

**Analogy for both methods**

- Event Flow: "I'll close the book on this chapter once I start reading the
  next chapter" (needs forward progress in the story).
- Event Timer: "I'll close the book on this chapter if nobody's turned a
  page in N minutes" (needs a pause in activity).

## Cadence (legacy, avoid)

Aggregates strictly on New Relic's internal wall clock at fixed intervals,
ignoring data timestamps entirely. Vulnerable to clock skew on the data
producer side (e.g. browser PageAction events). Prefer Event Flow or Event
Timer instead, unless producer clock skew is unavoidable and uncorrectable.

## Quick comparison

| | Event Flow | Event Timer |
|---|---|---|
| Trigger to close window | A later timestamp arrives | A countdown expires with no new data |
| Best for | Steady, frequent, in-order data | Sporadic, bursty, infrequent/batch data |
| Setting name | Delay | Timer |
| Typical use case | APM/Infra agent metrics, live CloudWatch streams | Error counts, polled cloud data, usage stats |
| Risk if misused | Can stall if data stops arriving | Can evaluate too early/late if timer poorly tuned |

Source: New Relic docs — "Choose your aggregation method" and "Streaming
alerts: key terms and concepts".

# New Relic NRQL Alert Streaming Methods: Event Timer (deep dive)

Companion entry to the Event Flow deep dive. Event Timer shares the same
fixed, wall-clock/epoch-aligned windowing concept as Event Flow (confirmed
directly from New Relic docs wording, e.g. "the 12:00-12:01 window" — not
windows anchored to whenever the first data point happens to arrive). The
only difference between the two methods is the trigger condition used to
decide a window is done.

**Event Timer rule:** a window only "wakes up" once its first data point
arrives. That starts a countdown timer (the configured `timer` value)
dedicated to that specific window. Every subsequent data point landing in
the *same* window resets the timer back to full. If the timer ever reaches
zero with no new arrivals for that window, the window is aggregated and
evaluated right then — driven by the clock, not by waiting for another data
point to show up.

Contrast with Event Flow:
- Event Flow: needs a *later data point to arrive* to confirm a window is
  done (progress driven by new data showing up).
- Event Timer: needs *silence* — absence of new data for long enough — to
  confirm a window is done (progress driven by elapsed time).

Each window's timer is independent: a data point landing in a different
window has zero effect on an earlier window's timer (unlike Event Flow,
where a later window's data is exactly what closes an earlier one).

**Worked example.** Settings: window duration = 1 minute, timer = 2
minutes. Alerting on sporadic error counts:

| Point | Timestamp |
|---|---|
| err1 | 12:00:10 |
| err2 | 12:00:40 |
| err3 | 12:03:15 |
| err4 | 12:03:20 |
| err5 | 12:03:50 |
| err6 | 12:10:00 |

Bucketed into the same kind of fixed windows as Event Flow:

| Window | Contains |
|---|---|
| 12:00-12:01 | err1, err2 |
| 12:03-12:04 | err3, err4, err5 |
| 12:10-12:11 | err6 |

Timer trace per window:

- Window 12:00-12:01: err1 at 12:00:10 starts the timer (would expire
  12:02:10). err2 at 12:00:40 resets it (new expiry 12:02:40). No more
  errors land in this window, so the timer runs out uninterrupted.
  **Evaluated at 12:02:40** — purely because the clock ran out, no new data
  point needed to trigger it.
- Window 12:03-12:04: err3 at 12:03:15 starts the timer (expiry 12:05:15).
  err4 at 12:03:20 resets it (expiry 12:05:20). err5 at 12:03:50 resets it
  again (expiry 12:05:50). No more arrivals. **Evaluated at 12:05:50.**
- Window 12:10-12:11: err6 at 12:10:00 starts the timer (expiry 12:12:00).
  No more arrivals. **Evaluated at 12:12:00.**

Windows with no data in them (e.g. 12:01-12:03) never start a timer at all
— they're simply skipped (this is where loss-of-signal settings matter, for
detecting total silence rather than per-window silence). A burst of
closely-spaced points (err3, err4, err5) keeps resetting the same window's
timer so the whole burst gets aggregated together into one evaluation,
instead of being fragmented across multiple evaluations.

**Ordering guarantee** (confirmed from New Relic docs): "If the timer for a
later data point elapses before an earlier data point, the event timer
method waits for the earlier timer to elapse before aggregating the later
data point." So even though each window's timer runs independently,
windows are still evaluated in order — a later window's result cannot jump
ahead of an earlier, still-pending window. This matters for anything
downstream relying on sequential signal history, like loss-of-signal
detection and gap filling.

**Tuning tip** (from docs): timer should be >= window duration. If the
timer is shorter than the window duration and data is irregular, a window
might get evaluated before all its data points have actually arrived,
leading to incomplete aggregation and a potentially false or missed alert.

**Quick mental model:**
- Event Flow: "Tell me when the next chapter starts, then I'll know this
  one's done."
- Event Timer: "If nobody's turned a page in N minutes, I'll assume this
  chapter is finished — even if no one ever starts the next one."

Source: New Relic docs — "Streaming alerts: key terms and concepts"
(Event timer section, explicit window example "the 12:00-12:01 window").
